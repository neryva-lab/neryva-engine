# The Product Registration Contract — How Any Product Integrates

**Status:** Plan of record (the heart of the architecture) · **Date:** 2026-08-23
**Bound by:** [ADR-002](../decisions/ADR-002-product-taxonomy.md), [ADR-003](../decisions/ADR-003-backend-topology.md). This file is the contract a product "signs" to exist on the platform. **If integrating a product requires changing the identity plane, the console shell, or another product, this contract or the product's use of it is wrong.**

## The four artifacts every product ships

1. **A manifest** (static, versioned, reviewed like an ADR — registered in `product_manifests`, seeded per deployment):
```yaml
key: deployment
version: 1
display_name: Neryva Deployment
category: orchestration
icon: deployment
brief: "Pipelines, environments and rollout orchestration for agents."
docs_url: https://neryva.com/products/deployment
faces:                      # which API faces it uses (ADR-003 D2)
  control: true             # console pages
  runtime: true             # public API / jobs
  consumer: false           # no end-user surface
console:
  base_route: /console/deployment
  nav:                      # contributed nav (rendered inside product pages)
    - section: Delivery
      items: [pipelines, deployments, environments]
    - section: Operations
      items: [infrastructure, logs, alerts, cost, secrets, compliance]
scopes: [deployment:read, deployment:write, deployment:operate]   # product scopes
entitlements:               # codes registered in product_entitlements
  plans: [deployment-usage]
summary_provider:           # control-plane endpoint the shell calls for the card
  route: /console/deployment/summary
  cache_seconds: 60
metering:
  product_tag: deployment   # REQUIRED on every spend event the product emits
runtime_routes:             # public routes this product owns (runtime plane)
  - /v1/deployments/**
```

2. **A summary provider** — one endpoint per product returning the console-home card:
```json
GET /console/deployment/summary   →
{
  "product": "deployment",
  "status": "active",
  "kpis": [
    {"label": "Active pipelines", "value": "6", "delta": {"value": "+2", "positive": true}},
    {"label": "Deploys this week", "value": "41", "delta": {"value": "+8%", "positive": true}},
    {"label": "Rollback rate", "value": "1.9%", "delta": {"value": "-0.4pt", "positive": true}}
  ],
  "alerts": [{"severity": "warn", "text": "2 environments near quota"}],
  "primary_cta": {"label": "Manage", "route": "/console/deployment/pipelines"}
}
```
The KPI schema is fixed by the console (label, value, delta, optional alert row) — cards are uniform, exactly like platform dashboards. Products with no data yet return `{status, kpis: []}`.

3. **An entitlement definition** — plans, trial length, limits (feeding the quota engine, which today enforces the `platform > tenant > surface > end_user` hierarchy and is extended per [partitioning.md](../partitioning.md) with `product` and `project` levels), per [ADR-002]'s register. The entitlement state machine (`none → trial → active → past_due → suspended → expired`) is **platform-owned**; products read state, never manage it.

4. **A metering tag** — every spend event the product causes carries `product_tag`. This is what makes usage views, billing, and cost anomaly detection per-product with zero platform changes.

## The contract composition rule (who owns the public API surface)

The single pinned contract (`contracts/openapi/openapi.v1.json`, regenerated by the export script — 103 paths today) remains the **one source of truth for the entire public surface**, platform and products alike. Product route ownership does not split the file; it *tags* it:

- Every path carries `x-neryva-owner: <platform | product key>`. Platform owns identity/org/console-furniture paths; each product owns its `console.base_route` + `runtime_routes` paths.
- **CI enforces bijection:** every route registered by a manifest must appear in the contract, every contract path's owner must be a registered key, and no route may exist outside a manifest (the 404 rule). No shadow routes, no stale paths, no product silently reshaping another's surface.
- **Versioning:** a product's paths version with its manifest version (breaking changes ride that product's review); platform-owned paths version with the platform. The contract pin in CI fails on any unowned or unregistered change.
- Future SDK facets filter by owner (one SDK per product + the platform SDK) without splitting the source spec.

## What the platform gives every product (the inheritance list)

| Platform service | Product gets |
|---|---|
| Identity (L1–L5, ADR-001) | Console login, step-up MFA, API keys scoped to its `scopes`, agent identities for its jobs |
| Tenancy/RLS | Row-level tenant isolation for its schemas, free |
| Gateway + guardrails | LLM access, routing, safety — products never hold provider keys |
| Policy engine | Their console actions and runtime calls are policy-evaluated like everyone else's |
| Metering/quota | Spend events, per-org/project/product usage, limits |
| Worker/queue | Background jobs (deployment runs, evaluations, digests) |
| Observability/audit | Metrics, traces, hash-chained audit of every privileged act |

A product's own code = its schemas + its console pages + its business logic + its summary provider. Nothing else.

## The integration checklist (same for product #2 and product #20)

1. ADR amendment to [ADR-002]'s register (the deliberate friction — product strategy is not a route).
2. Create `app/products/{key}/` module: schemas, console routes (`/console/{key}/**`), runtime routes if declared, summary provider, nav contribution.
3. Register the manifest; define entitlement plans + limits in the quota engine.
4. Emit spend events with the product tag from day one.
5. Console: mount the lazy route chunk; shell code change count: **zero**.
6. Website: a marketing page if desired (packaging view — no backend meaning, per ADR-002).

## Enforcement (what keeps this a contract, not a convention)

- **CI import rules** (ADR-003): products may import platform services; nothing may import products; products may not import each other — cross-product needs go through the public contract.
- **Route ownership:** the platform 404s any route not declared in a manifest (`console.base_route`, `runtime_routes`) — undeclared surface is impossible, not merely discouraged.
- **Manifest review:** manifest changes ride the same review bar as ADRs (they add public surface and entitlement meaning).
- **Contract tests:** each product must pass the summary-provider schema test and the entitlement-state rendering test; the console shell runs against a fake product in CI so the contract cannot silently drift.

## Worked example — how this answers "where does Deployment go?"

Deployment (see `../products/deployment/plan.md`) ships a module with pipeline/environment/run schemas, console pages for the nav above, a runtime API + worker jobs for execution (using L5 agent identities as runner credentials), the summary card shown above, entitlement `deployment-usage`, metering tag `deployment`. It declares `consumer: false`, so it gets no consumer surface anywhere. Nothing in the identity plane, console shell, or Agent Studio changes. That is the whole integration — by design.
