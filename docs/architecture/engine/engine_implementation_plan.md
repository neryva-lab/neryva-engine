# Neryva Engine implementation plan

## Document status

- Status: proposed implementation plan
- Owner: Engine platform team
- Depends on: [Engine architecture](./engine_architecture.md), [Agent Studio architecture](../agent_studio/agent_studio_architecture.md), [Neryva MCP plan](../neryva_mcp/neryva_mcp_implementation_plan.md)
- Rule: do not mark a phase complete until its exit gates and evidence exist in CI or an operational runbook.

## Definition of done

The Engine is production-ready only when all of the following are true:

- A tenant-scoped request cannot read or mutate another organization’s data through any public, MCP, worker, object, search, or cache path.
- PostgreSQL constraints and RLS tests pass with application, worker, table-owner, and bypass-role scenarios.
- User message acceptance, run creation, and outbox publication are atomic.
- Duplicate API requests, broker redelivery, worker retries, and provider retries do not create duplicate user-visible results or duplicate billable effects.
- A crashed worker can resume or safely reconcile each supported operation.
- Agent Studio can interact only through the versioned Neryva MCP contract and scoped capability.
- Public API schemas, error codes, pagination, idempotency, concurrency, and event cursors are documented and tested.
- Assistant versions, policies, usage records, audit records, exports, and deletions have explicit lifecycle semantics.
- Files are private, scanned, checksum-verified, tenant-bound, and never parsed in the API process.
- Sensitive data is encrypted in transit and at rest, and secrets are never stored in plaintext application configuration or logs.
- Restore, replay, deletion, and reconciliation drills have passed in an isolated environment.
- Security, load, chaos, and dependency/supply-chain checks run before release.

## Phase 0 — Architecture, threat model, and repository foundation

### Objectives

Turn the architecture decision into enforceable repository rules before implementing business features.

### Deliverables

- Engine ADR index and decision records for:
  - modular monolith and deployment roles
  - tenant model and RLS strategy
  - public REST/OpenAPI contract
  - Neryva MCP authority integration
  - outbox/inbox and transport choice
  - PostgreSQL migration policy
  - object-store upload and claim-check policy
  - identity provider integration
  - billing ledger authority
  - retention, deletion, legal hold, and recovery
- STRIDE-style threat model covering:
  - browser and channel clients
  - public API
  - service identities
  - Agent Studio and MCP capability tokens
  - PostgreSQL and RLS
  - object storage and signed URLs
  - queues, outbox, and event replay
  - provider and billing integrations
  - support/operator access
- Data classification: public, internal, confidential, restricted customer content, credentials, security audit.
- Repository quality baseline:
  - strict TypeScript compiler settings
  - formatting, linting, unit test, integration test, and coverage commands
  - dependency lockfile and update policy
  - environment/configuration schema
  - structured logger and request context
  - OpenTelemetry bootstrap before application imports
  - CI checks for generated contracts and migration safety
- Local development stack for PostgreSQL, object storage, Redis/Valkey, and optional NATS/Temporal.

### Exit gates

- Threat model has owners for every high-risk control.
- A pull request cannot add a route without a request schema, response schema, authorization declaration, and test.
- A pull request cannot add tenant-owned data without a tenant key, index plan, lifecycle policy, and isolation test.
- Configuration fails closed on missing secrets, invalid URLs, unsafe production defaults, and unsupported protocol versions.

## Phase 1 — Platform kernel and database safety

### Objectives

Create the small shared kernel that every module uses without making it a generic abstraction maze.

### Implementation

- Bootstrap Fastify with:
  - request ID and trace propagation
  - authentication pre-handler
  - route schema registration
  - response serialization
  - error mapping
  - rate-limit hook
  - graceful shutdown
  - readiness/liveness endpoints
- Implement configuration as a typed immutable object loaded once at startup.
- Implement database access:
  - PostgreSQL connection pool with bounded size and timeouts
  - Kysely typed database handle
  - transaction helper with explicit isolation/lock options
  - statement timeout and idle-in-transaction timeout
  - migration runner executed once by release job, never by every API replica
  - separate read-only and worker credentials where useful
- Define SQL conventions:
  - UUIDv7 or another time-sortable opaque ID generated by the application/database boundary
  - UTC `timestamptz`
  - explicit `created_at`, `updated_at`, and lifecycle timestamps
  - foreign keys for authoritative relationships
  - check constraints for state and quantity invariants
  - partial/covering indexes based on query evidence
  - no unbounded JSON blobs for query-critical fields
- Implement tenant context transaction setup and RLS test helpers.
- Implement structured errors with stable code, public message, HTTP status, retryability, and internal cause.
- Implement an internal clock/randomness port for deterministic tests.

### Exit gates

- Fresh database migration and rollback/recovery procedure pass in CI.
- `EXPLAIN` plans exist for baseline list, lookup, authorization, event, and message queries.
- Connection exhaustion and slow-query tests prove the API fails predictably.
- RLS negative tests pass for every initial tenant-owned table.
- No route serializes a database row directly.

## Phase 2 — Identity, organization, and authorization

### Objectives

Provide secure principals and organization-scoped access before exposing product data.

### Core data

Implement:

- `users`
- `external_identities`
- `organizations`
- `organization_domains`
- `memberships`
- `roles` and role assignments
- `service_accounts`
- `api_credentials` (hashed secret material only)
- `sessions` or session references where Engine owns browser sessions
- `authorization_policies` and immutable policy versions where needed
- `security_events`

### Authentication

- Integrate OIDC for browser and supported API clients.
- Add SAML through the identity provider for enterprise SSO; do not implement SAML in Engine.
- Use Authorization Code + PKCE for public clients.
- For same-origin browser applications, prefer secure, HttpOnly, SameSite cookies with CSRF protection.
- Validate issuer, audience, signature, clock skew, nonce/state, token expiry, and key rotation.
- Map IdP subject plus issuer to a local user; never use mutable email as the durable identity key.
- API keys and service credentials are shown once, stored as salted hashes, scoped, revocable, expirable, and audited.
- Use separate service identity credentials for Agent Studio, workers, billing reconciliation, and support operations.

### Authorization

Implement a decision pipeline:

```text
authenticated principal
  -> organization membership and status
  -> role/capability check
  -> resource ownership and relationship check
  -> policy/approval check
  -> database transaction and RLS
```

Do not use an organization role as proof that a user can access every nested resource if resource sharing or delegated access exists. Model those relationships explicitly. Start with Engine RBAC plus resource checks and RLS. Evaluate OpenFGA only when a measured domain need appears.

### Exit gates

- Membership revocation takes effect for new requests immediately according to the documented consistency policy.
- Disabled users, deleted organizations, expired credentials, and revoked service identities are rejected.
- Cross-tenant authorization fuzz tests pass for every route.
- SSO login, callback failure, logout, key rotation, and account-linking tests pass.
- Support access is an explicit audited action and cannot be performed through a customer token.

## Phase 3 — Organizations, assistants, policies, and publication

### Objectives

Make organization configuration immutable at runtime and safely consumable by Agent Studio.

### Data and behavior

- Organization settings:
  - display/brand configuration
  - data-region and isolation tier
  - model/provider allowlist
  - quotas and entitlements
  - retention defaults
  - allowed channels and integrations
- Assistant:
  - stable assistant identity
  - draft configuration
  - immutable version records
  - publish/unpublish state
  - rollback pointer
  - validation result
- Policy:
  - input/output policy references
  - tool permissions
  - approval requirements
  - data-source permissions
  - budget and timeout limits
  - version and effective timestamps

Every run is pinned to one assistant version and policy snapshot. Editing a draft must not mutate a published version. Publish is an atomic pointer change after validation. Rollback points to an existing immutable version; it does not rewrite history.

### Validation

- JSON Schema for the public configuration format.
- Domain validation for model/tool references, limits, dangerous combinations, and policy completeness.
- Capability registry validation against Model Gateway and Tool Gateway contracts.
- Redaction and secret scanning before persistence of instructions/configuration.
- Test conversation endpoint that uses a non-production budget and marks generated data as test data.

### Exit gates

- Concurrent publish/update tests cannot publish a partially written version.
- A running agent remains pinned to its original version after a new version is published.
- Invalid model, tool, knowledge, policy, and quota references are rejected before publish.
- Version export/import is deterministic and includes schema version.

## Phase 4 — Conversations, messages, runs, and canonical events

### Objectives

Implement the product’s durable conversation boundary and the Engine side of run creation.

### Message rules

- Engine issues `conversation_id`, `message_id`, and monotonic conversation sequence.
- A conversation has an organization, channel binding, participant scope, lifecycle, and current version.
- A user message is immutable after acceptance except through explicit redaction/moderation workflow.
- Assistant messages are committed by Engine after authorized completion; partial token deltas are not canonical messages.
- Tool calls/results and citations are durable semantic records with bounded payloads or claim-check references.
- All content rows carry a content classification and retention reference.

### Start-message transaction

```text
authorize conversation and assistant
  -> verify expected conversation version / active-turn policy
  -> insert user message
  -> insert Engine run projection in ACCEPTED state
  -> insert outbox RunCreated event
  -> commit
```

The response returns message/run identifiers and an event cursor. The caller may retry with the same idempotency key and receives the original result.

### Conversation concurrency

Choose and document the initial policy: one active user turn per conversation. Enforce it with a database uniqueness/lease invariant, not only an in-memory mutex. If parallel turns are introduced later, use independent branch/turn identifiers and define merge order before implementing UI behavior.

### Engine run projection

The Engine stores business-facing run state such as accepted, dispatched, running, waiting for approval, completed, failed, canceled, and expired. Agent Studio/Temporal owns execution details and checkpoints. Projection updates are monotonic and fenced by run generation/lease so a stale worker cannot close a newer attempt.

### Exit gates

- Duplicate message submission creates one user message and one run.
- A stale conversation version returns conflict without creating a message.
- Concurrent turn attempts follow the documented one-turn policy.
- Final assistant message and Engine run completion commit atomically.
- Replayed event delivery cannot duplicate user-visible messages.
- API reads return stable cursor pagination and reconnectable event cursors.

## Phase 5 — Neryva MCP authority and Agent Studio integration

### Objectives

Implement the Engine half of the existing Neryva MCP contract without leaking database access or provider details.

### Engine responsibilities

- Authenticate the Agent Studio workload identity.
- Validate protocol version and method capability.
- Issue and validate short-lived run-scoped capabilities.
- Confirm organization, conversation, run, assistant version, and policy snapshot match Engine records.
- Return authorized context references/data through bounded responses.
- Accept idempotent runtime events and update durable projections.
- Store opaque checkpoint references/payloads with size and retention limits.
- Validate memory proposals and tool/approval requests.
- Commit final assistant message plus run completion atomically.
- Reject events after terminal state or from stale run generations.
- Expose durable event observation and cursor replay.

### Prohibited behavior

- Agent Studio database credentials.
- Model-controlled arbitrary Engine commands.
- Neryva MCP method that bypasses Engine authorization.
- Unbounded conversation/document payload in an RPC or workflow argument.
- Treating a producer-local event sequence as the canonical Engine sequence.
- Assuming exactly-once delivery.

### Failure cases to implement first

- Studio process crashes after tool side effect but before acknowledgement.
- MCP response is lost after Engine commits a final message.
- Duplicate event with same idempotency key but different payload.
- Capability expires during a long run.
- Assistant version is unpublished while a run is executing.
- Organization membership/policy is revoked during a run.
- Engine accepts a message but dispatcher is down.
- Studio sends events after cancellation or terminal completion.

### Exit gates

- Neryva MCP conformance suite passes against Engine and Studio adapter.
- Scope-confusion tests cannot change tenant, conversation, actor, or assistant version.
- Completion retry returns the same committed result.
- Capability rotation and revocation tests pass.
- No MCP request requires direct SQL outside Engine application modules.

## Phase 6 — Outbox, inbox, broker, and asynchronous workers

### Objectives

Make every asynchronous boundary durable, observable, and replay-safe.

### Implementation

- `outbox_events`:
  - event ID
  - aggregate type/id
  - organization ID
  - event type/version
  - payload or claim-check reference
  - partition/order key
  - status/attempt metadata
  - next attempt time
  - trace/correlation IDs
- `inbox_events`:
  - consumer name/version
  - event ID
  - first/last received time
  - processing status/result reference
  - unique consumer/event key
- Delivery worker:
  - claim with lease
  - bounded batch
  - publish/ack timeout
  - exponential backoff with jitter
  - dead-letter state after policy threshold
  - replay command requiring operator authorization
- Consumer handler:
  - validate event version
  - enforce tenant scope
  - deduplicate before side effects
  - transactionally write result and next outbox event where required
  - record failure class and retryability

Use PostgreSQL polling first if volume is low. Add NATS JetStream when replay/fan-out/consumer isolation is required. Use stable event IDs and explicit ordering keys; do not promise global ordering. If Debezium is later introduced, preserve the same outbox schema and event semantics.

### Worker families

- Agent run projection and event observation
- Notifications and channel delivery
- Knowledge ingestion coordination
- Webhook delivery
- Usage and billing reconciliation
- Export generation
- Retention and deletion steps
- Orphan cleanup and integrity repair

### Exit gates

- Crash/restart/redelivery tests prove idempotent handlers.
- Outbox lag and dead-letter alerts fire in a test environment.
- A replayed event cannot cross tenant boundaries or double-charge usage.
- Ordering guarantees are tested per aggregate key.
- Backpressure prevents one tenant or consumer from starving others.

## Phase 7 — Files, uploads, knowledge, and claim-check storage

### Objectives

Provide secure large-payload handling and a rebuildable knowledge pipeline.

### Upload implementation

- Create an upload session only after authorization and quota check.
- Generate a random, tenant-bound object key; never use the user filename as the object key.
- Bind signed URL scope to exact key, method, content length, content type, checksum where possible, and short expiry.
- Support multipart uploads above the selected threshold; abort stale multipart sessions.
- On completion, verify object metadata server-side and transition to `UPLOADED`.
- Scan in quarantine; reject encrypted archives or unsupported formats according to policy.
- Parse in a sandbox with resource and output limits.
- Persist source hash and parser version so results are reproducible.

### Knowledge data

- `knowledge_sources`, `documents`, `document_versions`, `chunks`, `embeddings`, `retrieval_acl`
- Derived chunks always reference a document version and source range.
- Retrieval filters tenant and ACL before ranking/vector scoring.
- Indexing is versioned and can be rebuilt from canonical objects/documents.
- A deleted or quarantined source is removed from retrieval before physical purge completes.

### Claim-check contract

All large payload references include:

```text
artifact_id
organization_id
owner resource and purpose
content type
byte length
sha256
encryption key/version reference
created/expiry timestamps
retention class
```

Dereference requires a fresh Engine authorization check. A reference is not a bearer permission by itself.

### Exit gates

- Oversize, wrong MIME, checksum mismatch, malicious archive, and parser timeout tests pass.
- Signed URLs cannot read/write another tenant’s object.
- Ingestion can resume after each stage failure without duplicate chunks.
- Search never returns a non-ready, deleted, quarantined, or unauthorized document.
- Rebuild-from-source test produces equivalent indexed metadata.

## Phase 8 — Billing, quotas, entitlements, and reconciliation

### Objectives

Make quotas and billing explainable, idempotent, and independent of provider callback timing.

### Implementation

- Product catalog and entitlement snapshots.
- Organization plan/subscription mapping.
- Quota dimensions: requests, model tokens, model cost, storage bytes, ingestion work, tool operations, seats, and rate.
- Immutable `usage_ledger` with:
  - source event ID
  - usage kind/unit/quantity
  - organization and principal
  - run/message/reference
  - provider/model/resource metadata
  - idempotency key
  - estimated and settled cost
  - reconciliation state
- Atomic quota reservation/release or append-only usage accounting, chosen per dimension.
- Stripe/payment-provider adapters behind a billing port.
- Webhook inbox with signature validation, timestamp tolerance, dedupe, and replay handling.
- Daily/hourly reconciliation job comparing provider records, Engine ledger, and entitlements.
- Operator correction workflow using compensating ledger entries.

### Exit gates

- Duplicate usage events are ignored.
- A payment-provider webhook cannot directly grant access without validated Engine reconciliation.
- Quota decisions remain deterministic during provider outage.
- Billing discrepancies are detectable and correctable without rewriting history.
- Cost and usage data can be explained from a run to a ledger entry to an external invoice/meter record.

## Phase 9 — Audit, retention, export, legal hold, and deletion

### Objectives

Treat data lifecycle as a product capability, not a database cleanup script.

### Implementation

- Retention classes per organization/resource/data type.
- `retention_policies`, `legal_holds`, `export_requests`, `deletion_requests`, `purge_tasks`.
- Export workflow that:
  - authorizes the requester
  - creates a point-in-time manifest
  - includes canonical records and object references permitted by policy
  - writes encrypted archive to private storage
  - exposes status and one-time signed download
  - records completion and expiry
- Deletion workflow that:
  - verifies scope and holds
  - marks resources unavailable to product/search first
  - emits deletion events for derived stores
  - deletes objects and derived indexes
  - records tombstones needed to reject stale references
  - verifies completion and reports exceptions
- Audit log:
  - actor/service identity
  - organization/resource/action
  - decision/result
  - timestamp and request/trace IDs
  - reason/change summary
  - before/after hashes or safe summaries, not unrestricted sensitive payload
- Optional immutable/WORM archive for compliance audit exports.

### Exit gates

- Legal hold blocks eligible purge while allowing unrelated retention work.
- Deletion removes data from API, retrieval, cache, object storage, and derived indexes according to policy.
- Export does not include another tenant’s data and expires safely.
- Audit records survive ordinary application-row deletion and support operator review.
- A deletion/recovery drill produces an evidence report.

## Phase 10 — Enterprise operations and production hardening

### Security

- Map OWASP ASVS 5.0.0 controls to requirements, code, and tests.
- Run SAST, dependency/license scanning, secret scanning, SBOM generation, container scanning, and DAST.
- Require signed build artifacts and protected deployment approvals.
- Rotate database, IdP, broker, object-store, provider, and service credentials.
- Red-team tenant isolation, prompt/tool boundary, signed URL, webhook, support access, and deletion paths.

### Reliability

- Define SLOs and alert thresholds from load-test evidence.
- Add database pool, lock, slow-query, broker, worker, object, and provider dashboards.
- Test graceful shutdown and rolling deployments with active SSE and worker leases.
- Test dependency degradation: cache down, broker down, object storage slow, provider timeout, IdP key rotation, billing provider outage.
- Define dead-letter and replay runbooks.

### Disaster recovery

- Managed PostgreSQL HA, continuous archiving, and point-in-time restore.
- Object versioning/lifecycle and cross-region strategy by tenant tier.
- Rebuildable search/index layer.
- Restore rehearsal on a schedule with measured RPO/RTO.
- Document region failover and tenant placement behavior.

### Exit gates

- Production release has a signed security, migration, restore, and rollback checklist.
- Chaos tests cover API replicas, worker crashes, broker redelivery, database failover, and provider failure.
- DR rehearsal meets the declared RPO/RTO or produces an explicit remediation plan.
- On-call can identify, pause, replay, or quarantine a failing tenant/job without direct production SQL.

## Phase 11 — Optional scale and isolation extensions

Only enter this phase from measurements or a contractual requirement.

- Move high-volume event fan-out to Debezium/Kafka if outbox polling and NATS no longer meet throughput/replay requirements.
- Add OpenFGA for relationship-heavy authorization with an explicit consistency and revocation design.
- Move selected tenants to dedicated database/object/index cells.
- Add dedicated search/vector infrastructure after benchmarked PostgreSQL limits.
- Isolate high-risk tools or customer-authored code into a sandbox service.
- Split a module into an independently deployed service only with a written ownership, data, failure, and migration plan.

Do not use this phase to hide unclear boundaries in v1. A service split is successful only when the new boundary improves security, reliability, scaling, or team autonomy without creating a second source of truth.

## API and event contract checklist

Every public endpoint must specify:

- authentication requirement
- organization/resource scope
- request/response JSON Schema
- maximum body and field sizes
- idempotency behavior
- concurrency behavior
- pagination/cursor behavior
- error codes and retryability
- audit event
- rate-limit class
- data classification and retention impact
- OpenTelemetry span attributes with cardinality limits

Every event must specify:

- stable event ID
- event type and schema version
- source and subject/aggregate
- organization scope
- ordering key
- causation/correlation IDs
- payload size/claim-check rule
- consumer idempotency key
- retention and replay policy
- authorization implications

## Test strategy

### Unit tests

Test domain state transitions, validators, entitlement math, policy evaluation, idempotency decisions, pagination cursors, error mapping, and retention eligibility without a network dependency.

### Integration tests

Run against real PostgreSQL, object storage emulator/service, Redis/Valkey, and NATS/Temporal where the behavior depends on their semantics. Test migrations, RLS, locks, constraints, signed URLs, transaction rollback, and timeouts.

### Contract tests

- OpenAPI schema tests for route compatibility and response filtering.
- Neryva MCP generated-client/server conformance.
- Provider/billing/webhook adapter contract fixtures.
- Event schema compatibility and unknown-field behavior.

### Isolation tests

Use two organizations and multiple principals/roles. Test every route, worker, event consumer, cache key, object path, retrieval query, export, support operation, and deletion path for cross-tenant access.

### Property and concurrency tests

- Arbitrary duplicate/reordered event delivery.
- Repeated idempotent command with lost responses.
- Concurrent publish, message submission, cancellation, completion, and deletion.
- Lease expiry and stale worker fencing.
- Ledger compensation and reconciliation invariants.
- Cursor replay with gaps/duplicates.

### Failure and chaos tests

- Kill API/worker after each durable write boundary.
- Drop network responses after remote side effects.
- Delay/reorder broker messages.
- Make object storage, provider, billing, cache, and IdP unavailable.
- Fail database connections during commit/rollback.
- Restart during migration-safe deployment.

### Performance tests

Measure tenant-skewed workloads, long conversation reads, event streams/reconnects, assistant publication, upload completion, ingestion throughput, authorization checks, outbox lag, quota checks, and billing reconciliation. Store workload, version, hardware, and p50/p95/p99 results with each benchmark.

- Database failover and point-in-time restore
- Migration rollback/forward-fix
- Outbox lag and dead-letter replay
- Stuck run projection or expired MCP capability
- Worker crash and lease recovery
- Provider outage and model failover
- Billing webhook outage and reconciliation
- Object-store orphan cleanup
- Malware quarantine and false-positive review
- Cross-tenant incident response
- Credential/key rotation
- Data export and deletion request
- Legal hold placement/removal
- Regional isolation and failover
- Security incident evidence preservation

## Release gates

The release pipeline must block on:

1. Typecheck, lint, formatting, and unit tests.
2. Migration apply on a clean database and upgrade from the previous release.
3. Integration, RLS, contract, and idempotency tests.
4. OpenAPI and Neryva MCP compatibility checks.
5. Dependency/license/security scans and SBOM.
6. Load smoke test and database query-plan regression check.
7. Restore/replay evidence for the release train.
8. Review of changed data classifications, audit events, retention behavior, and permissions.

## Final implementation order

The critical path is:

```text
threat model and platform kernel
  -> identity/tenancy/RLS
  -> assistant versioning and policy
  -> conversations/messages/runs
  -> Neryva MCP authority
  -> outbox/inbox and workers
  -> files/knowledge
  -> billing/usage
  -> lifecycle/audit
  -> hardening/DR
```

Do not begin with billing UI, a large tool catalog, arbitrary customer code, or microservice decomposition. The Engine’s highest-risk work is authority, transaction semantics, isolation, replay safety, and lifecycle correctness; those must be proven before breadth.
