## 0. Instructions to the implementing AI agent — READ FIRST, NO EXCEPTIONS

This section is a direct order from the repo owner. It outranks convenience, speed, and every paragraph below it. Violating any item here is a failed implementation, no matter how many features appear to work.

1. **Quality is the deliverable. There is no compromise on it.** A robust, state-of-the-art implementation with great attention to detail — not the fastest diff that turns the tests green. If a choice trades correctness for speed, you take correctness. Every time.
2. **Do not cheat, do not skip, do not paper over.** No mock data. No `toast.success('…queued')` in place of a mutation. No hardcoded catalogs standing in for live endpoints. No invented routes, fields, or error strings. No `setTimeout` simulations of server work. The current frontend is full of exactly these sins (§4 names them); your job is to delete them, not to imitate them.
3. **Verify firsthand, trust nothing secondhand.** Before you wire any endpoint, open the engine controller + service yourself and read the route, the `@Roles`, the DTO, and the return shape. This ledger cites file:line for every contract — re-open each cite at implementation time and confirm it still says what this ledger claims. If the engine moved, the engine wins and you update this ledger. Subagent summaries, stale comments, and your own memory are not evidence.
4. **Everything must be implemented correctly, completely, and robustly.** Full feature parity with the engine surface in §2 — every route listed has a UI surface or an explicit, owner-approved deferral recorded in this file. "The button exists" is not done; done is: correct request shape, correct headers (`X-Neryva-Org`, `Idempotency-Key` on mutations, `If-Match` on draft writes), role-gated affordance, loading/empty/error/denied states, verbatim server copy (§7), audit-visible outcome, and a passing gate (§10).
5. **You have full freedom to redesign.** The current setup UI was designed before the engine architecture existed and is less capable than the backend (§4). You are explicitly permitted — expected — to restructure views, add routes, split or merge sections, and introduce new components, hooks, and state wherever the engine contract deserves a better surface than exists today. Do NOT limit the feature set to what the current UI has. Do NOT be lazy: if the engine supports it and the spec wants it, build it.
6. **Be creative and intelligent, but never inventive about contracts.** Creativity belongs in information architecture, interaction design, progressive disclosure, empty states, guidance copy, and making complex machinery feel obvious. It never belongs in request/response shapes, role matrices, status codes, or error text — those are copied from the engine, byte for byte.
7. **Leave the codebase better than you found it.** One vocabulary-mapping module (never per view). One caps module. One error-extension point. Defensive parsers on every server read. No duplicated mutation logic. Delete every static JSON import and fake handler you replace — grep must prove they are gone (§10).
8. **When you find an engine contradiction, stop and surface it.** §3 lists six verified contract risks. You implement the service-truth behavior, you render the server's refusal verbatim, and you flag the item to the platform team with the exact file:line — you do NOT silently reshape the UI around a suspected engine bug, and you do NOT "fix" the engine from the frontend.

### 2.2 Payload contract — `E:src/modules/assistants/validation.ts` (full file read)

The engine payload (`assistantPayloadSchema`, `validation.ts:43-85`) — the ONLY vocabulary the wire may carry:

- `instructions?` string 1..32,768 (optional at type level; publish requires non-empty — `assertPublishable`, `validation.ts:154-160`).
- `model_params?`: `{temperature 0..2, max_output_tokens 1..200,000, top_p (0,1], reasoning_effort minimal|low|medium|high, output_schema (JSON-object string ≤16,384)}` — strict (unknown keys inside refuse at shape level).
- `budget_policy?` (strict): `{max_total_tokens 1000..2,000,000, max_cost_micros 0..10¹², wall_clock_seconds 0..86,400, max_tool_calls 0..1000, max_model_calls 1..200}`.
- `model_policy!`: `{allowed_models: string[1..20] (`provider/model` shape by convention — registry uses `anthropic/claude-sonnet-4-5`), fallback_enabled? default false}`.
- `context_policy!`: `{history_limit int 1..100 default 30, summary_enabled? default true, knowledge_sources? string[] default [], memory_scope? user|organization|conversation|none default user}`.
- `tool_policy!`: `{tools: [{name 1..64, access read|write REQUIRED, approval required|optional default optional, schema_hash? 64hex}] ≤50 default []}`.
- `knowledge_policy?`: `{retrieval_enabled? default false, max_results? int 1..20 default 5}`.
- `guardrail_policy!`: `{input_policy min1 default 'default', output_policy min1 default 'brand-safe', pii_redaction? default true}`.
- Unknown keys at ANY depth → 422 `unknown keys rejected (template-only extensions do not belong in the Engine payload): <dotted paths>` (`validation.ts:171-179` — explicit diff because non-strict zod strips silently).
- Secret shapes → 422 before persistence: credential-assignment values (`api_key: sk-…`) and secret-named keys carrying values (`validation.ts:90-134`).
- Global pipe: `whitelist: true, forbidNonWhitelisted: true` (`E:src/main.ts:123-128`) — unknown TOP-LEVEL DTO keys 400. (This is the mechanism behind R-1.)

Consumer→engine vocabulary map (single module, `agent-setup.md` §6 — engine truth confirms every line): approval `never|on_effect|always` → `optional|required` (+ catalog `approval_requirement` escalates at authorize time); `memory_scope: 'org'` → `'organization'` (engine `user` has no consumer value — omit it from the picker); `max_context_tokens`, `retrieval_policy`, `brand` are consumer-side only, NEVER on the wire; tool entries carry only `name/access/approval/schema_hash` (effect class lives on the catalog row).

**R-1 — Version writes vs. the DTO allowlist (HIGHEST RISK).** `CreateVersionDto` (`E:src/modules/assistants/dto.ts:111-130`) declares ONLY `model_policy, context_policy, tool_policy, knowledge_policy?, guardrail_policy`. Record the outcome in this ledger. The editor MUST keep instructions/model-params/budget editable; a "policies-only" editor is a spec violation.

**R-2 — Formal evaluate requires PUBLISHED (`E:src/modules/knowledge/eval.service.ts:305-307`).** Both `POST eval/runs` and (via `evaluateVersion`) `POST versions/:v/evaluate` bottom out in `startRun`, which 422s (`assistant_version_id: 'must be a PUBLISHED version of this org'`) for drafts — in tension with the funnel order EVALUATE→PUBLISH (`agent-setup.md` §2) and with `evaluateVersion`'s draft-agnostic lookup. **Implementation stance:** the Evaluate action is available on every version; on the PUBLISHED-required 422 the UI renders the refusal verbatim with the fix path (publish first, then evaluate — and note the BLOCK/required-checks gates still protect the NEXT publish since they are content-hash keyed, `release-gate.ts:91-105`). Escalate the funnel tension to the platform team with these cites; do not hide the Evaluate button on drafts (that would enshrine the contradiction).

**R-3 — No eval-run detail endpoint.** Decision polling = `GET eval/runs?dataset_id` (filter client-side by `assistant_version_id`, newest `finished_at` wins) + version `provenance.last_evaluation`. Runs list caps at 100 (`eval.service.ts:349-358`). The UI polls with backoff while `state ∈ pending|running` and stops at terminal states. `POST …/results` is eval-worker-only — no UI.

**R-5 — Burn-rate is service-only.** No routes; operate UI surfaces rollout state + `paused_reason/by/at` + audit (`agent-setup.md` §7). Do NOT spec a burn-rate endpoint.

**R-6 — Two memory-delete paths.** `DELETE memories/:id` (owner,admin) vs `POST memories/:id/delete` (owner,admin,developer) (`knowledge.controller.ts:177-184`, `harness-parity.controller.ts:221-234`).
